# backe M4 — Git-Schicht und Schreibpfad Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Jeder Write von `backe` ist genau ein signierter Commit in der Arbeitskopie seiner Identität, ein abgebrochener Write hinterlässt nichts, und `verify` erkennt jede Identitätsanmaßung in der Historie seit dem Vertrauensanker.

**Architecture:** `src/git/` bekommt die Git-Bausteine ohne Fachlogik: Commit-Message, Repo-Zustand, signierter Commit über einen temporären Index, Rollback, lokale Zustandsdateien unter `.git/backe/`, Historie und Signaturen, SSH-Keys. `src/ops/verify-policy.ts` prüft die Identitätsregeln eines Commits rein, ohne I/O. Neu ist `src/services/` — die Use-Cases, die `ops`, `context`, `git` und `store` zusammensetzen: `initBacklog`, `executeWrite`, `verifyRange`, Arbeitskopien (`cloneBacklog`, `ensureWorkingCopy`, `addBacklog`, `removeBacklog`, `showBacklog`), `createAgent`, Quarantäne. `executeWrite` ist die einzige Stelle, die Dateien in einem Backlog schreibt und committet.

**Tech Stack:** wie M3; System-`git` (getestet mit 2.56) und `ssh-keygen`, beide nur über `src/git/exec.ts`.

**Spec:** `docs/proposals/backe.md` (§2.2, §2.12, §2.13, §2.14, §2.15.3, §2.16.1, §3.9, §3.10, §5), Gesamtplan `docs/superpowers/plans/2026-11-18-backe-gesamtplan.md`. Es gelten dessen Global Constraints, die Zeilen M4 in »Übernommen aus M1/M2/M3« und die Planentscheidungen; die Tasks wiederholen die Werte, die sie brauchen.

## Global Constraints

Alle Global Constraints des Gesamtplans und von M1–M3, dazu für M4:

- Schichten: `src/git/**` importiert nur `core`, `store` und `node:*`. `src/ops/**` bleibt ohne I/O. `src/services/**` importiert `core`, `store`, `context`, `git`, `ops` — nie `cli`, `mcp`. `child_process` nur in `src/git/exec.ts`.
- Signiert wird nur per `-c gpg.format=ssh -c user.signingkey=<key>` am einzelnen Aufruf; Git-Configs werden nicht geschrieben außer `git remote add` im neuen Repo. Kein Commit läuft durch Hooks (`commit-tree` statt `commit`).
- Autor und Committer eines Writes: Name = `name` des Users im Backlog, E-Mail = `<handle>@backe.invalid`, gesetzt über `GIT_AUTHOR_*`/`GIT_COMMITTER_*`.
- Netz- und Signier-Aufrufe (`commit-tree -S`, `clone`, `push`, `fetch`) bekommen `transportEnv(env)` = `HOME`, `SSH_AUTH_SOCK`, `GIT_SSH_COMMAND` aus dem Kontext-Env (`undefined` entfernt den Key) — nie still aus `process.env`.
- Pfade an Git immer nach `--` oder per `--pathspec-from-file=- --pathspec-file-nul`, mit `GIT_LITERAL_PATHSPECS=1`. Revisionen aus Eingaben laufen erst durch `resolveCommit` (`rev-parse --verify --end-of-options <rev>^{commit}`).
- Lokale Zustandsdateien liegen unter `git rev-parse --path-format=absolute --git-path backe` der Arbeitskopie (funktioniert auch mit `.git`-Datei): `anchor`, `verified`, `identity` (je eine Zeile mit `\n`), `write.lock`, `write.journal`, `allowed_signers/<tree>`.
- Lock-Reihenfolge: `write.lock` vor `config.lock`; `withFileLock` ist nicht reentrant, nichts unter `write.lock` holt ihn erneut.
- Fehlercodes: Lock gehalten, Arbeitskopie nicht auf dem Sync-Branch oder mitten in Rebase/Merge, ungesicherte Änderungen an betroffenen Pfaden, HEAD während des Writes bewegt → `conflict`; fremde Identität in der Arbeitskopie, Signieren fehlgeschlagen → `usage`; Backlog-Format neuer als `BACKLOG_FORMAT_VERSION` → `validation`; ungültige Historie → `verify`; Push/Clone über das Netz gescheitert → `sync`; fehlende Arbeitskopie ohne Quelle → `not_found`.
- Schritt 6 von §2.16.1 (Hintergrund-Sync nach dem Write) kommt mit M6; `executeWrite` startet nichts nach.
- Tests: echtes `git`, Bare-Remotes im Temp-Verzeichnis, kein Netz. Test-Keys erzeugt `testKey` einmal je Name und Testdatei. Das Test-Env enthält `HOME` und `BACKE_HOME` im Temp-Verzeichnis und kein `SSH_AUTH_SOCK`.
- Coverage-Gate `src/services/**`: `lines: 90, branches: 90` (Task 8 trägt es ein).

## Review Focus

1. **Abbruch mitten im Write** — Fehler, SIGINT oder Absturz zwischen Dateischreiben und Commit: Danach ist die Arbeitskopie sauber, kein halb geschriebenes Issue, der nächste Write läuft. → Task 8 `a failure after writing restores the working copy`, `SIGINT is deferred until the write finished`, `a journal left by a crash is rolled back by the next write`.
2. **Ungesicherte Hand-Edits in der Arbeitskopie** — eine geänderte Datei, die die Operation berührt, wird nicht still mitcommittet (`conflict`, nichts geschrieben, Hand-Edit unverändert); eine unbeteiligte Datei bleibt ungesichert und ungestaged, vom User vorgemerkte Änderungen bleiben vorgemerkt. → Task 5 `commit takes exactly the given paths`, Task 8 `a hand edit on an affected path is a conflict`.
3. **Zwei Prozesse derselben Identität schreiben gleichzeitig** (CLI und MCP-Server) — beide Commits landen nacheinander, linear, keiner verliert seine Operation. → Task 8 `concurrent writes are serialized`.
4. **Geteiltes `~/.backe` über Host- oder Container-Grenzen, Reboot** — ein Lock eines anderen Hosts wird nie automatisch übernommen (`conflict` mit Host und Pfad), ein Lock von vor dem Boot schon. → Task 2.
5. **Feindliche Historie** — ein Commit mit Symlink (`issues/7f/bk-7f3k2/issue.md → ~/.ssh/id_ed25519`), Submodule, Merge-Commit, umgeschriebener Historie oder gültiger Signatur, aber fremdem `Backe-Actor`: `verify` meldet jeden mit Grund; ein Write schreibt nie durch einen Symlink. → Task 1 `applyFileChanges refuses symlinked paths`, Task 9, Task 10.

## Spec-Fragen aus M2 — Festlegungen

Der Gesamtplan nennt fünf offene Fragen zum Identitätsschutz »vor M4«. `verify` übernimmt die Regeln aus `checkUserChange`, deshalb entscheidet dieser Plan sie (Task 6); der Spec bekommt sie nach Abnahme als Präzisierung von §2.12/§2.13.

| Frage | Festlegung | Preis |
| --- | --- | --- |
| Handle-Wiederverwendung nach `user.rm` (neuer User erbt Autorschaft alter Kommentare) | Einen Handle, dessen `users/<handle>.md` in der Historie schon einmal gelöscht wurde, legt nur ein Admin neu an | Wiederverwendung braucht einen Admin |
| Keys über Users nicht eindeutig | Ein neu eingetragener Key darf bei keinem anderen User in `keys` oder `revoked_keys` stehen (Vergleich ohne Kommentar) | Ein Key, den zwei Identitäten teilen sollen, geht nicht |
| Eigenen widerrufenen Key per `entity.edit` zurückholen | Widerruf ist endgültig: Einträge in `revoked_keys` bleiben, und ihr Key steht nicht wieder in `keys` — auch für Admins | Ein versehentlicher Widerruf heißt neuer Key |
| Operator gibt seinen Agent ohne Zustimmung weiter | Den `operator` ändern nur Admins | Übergaben laufen über einen Admin |
| Admin umgeht »Operator ist Mensch« per `kind`-Wechsel des Operators | Ein User, der Operator von Agents ist, wird nicht zum Agent — für alle | Erst die Agents umhängen |

      - anderer Branch: `<wc> steht auf <b>, erwartet <branch>`, hint `git -C <wc> switch <branch>`;
      - ungeboren: `<wc> hat noch keinen Commit`.

    6. Echten Index für die Pfade nachziehen: `reset -q --pathspec-from-file=- --pathspec-file-nul`.
    Liefert den neuen Commit.
  - `transportEnv(env: Env): Record<string, string | undefined>` in `git/exec.ts` exportiert (`HOME`, `SSH_AUTH_SOCK`, `GIT_SSH_COMMAND`).

      1. `anchor` fehlt → `verify` `Kein Vertrauensanker in <wc>`. `to` (Default `HEAD`) hat genau eine Wurzel, und die ist `anchor`; `verified` (falls vorhanden) ist Vorfahre von `to` — sonst `verify` `Historie von <to> passt nicht zum Vertrauensanker` bzw. `<to> ist kein Nachfahre des zuletzt verifizierten Stands <kurz>` (Force-Push).
      2. Bereich: ohne `since` alle Commits ab `anchor` inklusive; mit `since` die Commits nach `since`.
      3. Anker: keine Parents, `Backe-Op: init`, Akteur ist Admin laut eigenem Baum; die Signatur wird gegen die Users im eigenen Baum geprüft, Policy entfällt.
      4. Jeder andere Commit: Merge-Commit → `Merge-Commit`. Signatur gegen `allowed_signers` aus den nicht widerrufenen Keys der Users im Parent-Baum (`<handle> namespaces="git" <key>` je Zeile, sortiert), zwischengespeichert als `<stateDir>/allowed_signers/<users-tree>`; Commits mit gleichem Users-Baum im Parent in einem Aufruf. `N` → `unsigniert`; `B` → `Signatur ungültig`; sonst ohne `G`: Fingerprint in `revoked_keys` eines Users → `Key <fp> von <h> ist widerrufen`, sonst `Key <fp> gehört zu keinem User`.
      5. `Backe-Actor` fehlt → `Backe-Actor fehlt`, mehrfach → `Backe-Actor mehrfach`, ≠ Prinzipal → `signiert von <p>, Backe-Actor ist <a>`.
      6. `checkCommitPolicy` mit Parent- und Nachher-Stand; `removedHandles` nur berechnen, wenn der Commit einen User anlegt.
      7. `Backe-Op` fehlt oder ist nicht dekodierbar → Hinweis in `notices` (`<kurz>: Backe-Op fehlt`), kein Verstoß.
      8. Quarantäne: maßgeblich ist `.backe/quarantine.jsonc` im letzten Commit des Bereichs, der die Datei ändert und selbst gültig ist (ohne Quarantäne geprüft); ohne solchen Commit der Stand bei `since` bzw. keiner. Schemafehler der Datei → Grund `quarantine.jsonc ungültig: <meldung>` an dem Commit. Ungültige Commits mit Eintrag wandern nach `quarantined`.
      9. `record` und `invalid` leer → `verified` = `to`. `record` mit `since`, das nicht Vorfahre-oder-gleich von `verified` ist → `usage`.
    - `assertVerified(report: VerifyReport): void` → `BackeError('verify', '<n> ungültige Commits seit <anker kurz>', {details: report})`, wenn `invalid` nicht leer.
