# backe M2 — Operationen und Graph (`ops`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Jede Mutation von `backe` als serialisierbare Operation, die sich rein — ohne Git, ohne Dateisystem — gegen einen `BacklogSnapshot` prüfen und anwenden lässt, samt Batch, Übersetzung von Hand-Edits, deklarierten Properties und der Graph-Logik hinter `next`, `claim` und `rank`.

**Architecture:** `src/ops/` liegt über `core` und `store` und importiert nichts aus `git`, `context`, `services`. Kern ist ein `Draft`: eine Copy-on-Write-Sicht auf den Snapshot, in die jede Operation ihre neuen Entitätsstände schreibt; `Draft` prüft dabei Schema und Invarianten und erzeugt am Ende die `FileChange[]`. `applyOperation` ist ein Batch der Länge 1. Graph, Ordnung, Rank und Properties sind reine Funktionen über dem Snapshot.

**Tech Stack:** wie M1; neu nur `node:crypto` (`createHash`) in `src/ops/operation.ts`.

**Spec:** `docs/proposals/backe.md` (§2.4–2.13, §2.16.4–2.16.6, §2.17, §2.22–2.24, §5), Gesamtplan `docs/superpowers/plans/2026-11-18-backe-gesamtplan.md`. Die Global Constraints, die Abschnitte »Übernommen aus M1« (Zeilen M2) und die Planentscheidungen mit Meilenstein M2 des Gesamtplans gelten hier; die Tasks wiederholen die Werte, die sie brauchen.

## Global Constraints

Alle Global Constraints des Gesamtplans und von M1, dazu für M2:

- `src/ops/**` ist rein: kein `node:fs`, kein `child_process`, keine Uhr, kein Zufall außer über `ApplyContext` (`now`, `randomBytes`). Erlaubt: `core`, `store/layout.ts`, `store/frontmatter.ts` (Serialisieren), Typen aus `store/snapshot.ts` und `store/files.ts`, `node:crypto` nur für `createHash`.
- Kein Algorithmus über Graphen rekursiv — Stack-Tiefe darf nicht an der Länge einer `parent`- oder `depends_on`-Kette hängen.
- Fehler sind `BackeError` mit `details.reason: Violation` (Task 8); Code-Zuordnung laut Planentscheidung »Exit-Codes der Operationen«.
- Jedes Schreiben einer Entität geht über `serializeEntityFile(kind, data, body, extra)` **mit** `StoredEntity.extra` — unbekannte Keys gehen nie verloren.
- Coverage-Gate `src/ops/**`: `lines: 90, branches: 90` (Task 3 trägt es ein).

## Review Focus

1. **Operationen eines neueren Clients** — unbekannter `op`-Name oder unbekanntes Feld im Trailer: `decodeOp` lehnt ab (Exit-Code 2), statt das Feld still zu verwerfen und eine halbe Absicht anzuwenden. → Task 7, `decodeOp rejects unknown op names and fields`.
2. **Lange Ketten** — 10 000 Issues in einer `parent`- oder `depends_on`-Kette: Zykluserkennung, Vorfahren und Bereitschaft laufen ohne Stack Overflow. → Task 3, `long chains do not overflow the stack`.
3. **Hängende Referenzen** — eine kaputte Datei fehlt im Snapshot, andere Issues verweisen noch auf sie: Bereitschaft behandelt sie als nicht erledigt; Operationen, die die Referenz nicht neu setzen, laufen weiter. → Task 3, `missing dependency counts as unsettled`; Task 8, `existing dangling refs do not block unrelated edits`.
4. **Zeilenenden und Unicode in Texten** — ein Body mit CRLF aus einem Hand-Edit erzeugt keinen Scheinkonflikt; `\n`, `\r`, U+2028 und Emoji überstehen `encodeOp`/`decodeOp` in einer Trailer-Zeile. → Task 7, `trailer stays one line and roundtrips text`; Task 13, `crlf body edit is not a conflict`.
5. **Getypte Property-Werte von der Kommandozeile** — `--prop k:=1e999` (Infinity), `:=-0`, `:=null`, verschachteltes `__proto__`: Fehler mit Key im Text statt still verfälschter Werte. → Task 1, Task 6.

**Gemeinsame Semantik** (jede Operation, Tasks 8–11):

- Vorbedingung: Zielwert schon erreicht → No-op; sonst Ist-Wert ≠ `from` (bei Bodies: `bodyHash(ist) ≠ from_hash`) → `conflict`/`precondition`.
- `add`/`remove` auf Listen haben keine Vorbedingung; Vorhandenes hinzufügen und Fehlendes entfernen sind No-ops. Hinzufügen hängt hinten an. Leere Listen entfallen.
- Das Subjekt der Operation (Issue, Projekt, …) fehlt → `not_found`/`missing_ref`.
- Kommentare, die eine Operation erzeugt, schreibt der Akteur; Dateiname `commentFileName(ctx.now, ctx.actor, rnd)`, `rnd` = 3 Crockford-Zeichen aus `ctx.randomBytes`. Ist der Dateiname vorgegeben (`reason_file`, `file`, `blocker_comments`), muss sein Autorenteil `ctx.actor` sein (`validation`/`policy`), und `created` des Kommentars kommt aus dem Namen.

### Task 4: Auswahl für `next`

**Files:**
- Create: `src/ops/next.ts`, `src/ops/notice.ts`
- Test: `src/ops/next.test.ts`

**Interfaces:**
- Consumes: Task 3
- Produces:
  - `type NoticeCode = 'open_children' | 'forced_done' | 'blocker_deleted' | 'settled_dependency' | 'unblockable'`; `type Notice = { code: NoticeCode; message: string; ids: string[] }`
  - `type ContextFilter = { project?: string; projectExact?: boolean; sprint?: string; repo?: string }`; `matchesContext(issue: Issue, f: ContextFilter): boolean` — Projekt rekursiv (`web` umfasst `web/auth`, nicht `webapp`), Repo per Name vor dem `@`.
  - `type NextQuery = { actor: string; level: 'leaf' | 'top'; filter: ContextFilter }`
  - `type NextResult = { id?: string; resumed: boolean; reason?: 'waiting' | 'all_assigned' | 'all_blocked' | 'nothing_open'; waiting?: string[]; notices: Notice[] }`
  - `selectNext(s: BacklogSnapshot, q: NextQuery): NextResult`

Algorithmus (§2.22, §2.23; bei `level: 'top'` zählen überall nur Issues ohne `parent`):

1. **Eigene Arbeit:** Issues im Kontext mit `in_progress`, `assignee === actor`, kein Vorfahre `blocked`/`on_hold`; das erste nach `compareIssues` → `resumed: true`.
2. **Kandidaten:** im Kontext, `isReady(…, { level })`, `assignee` leer oder `actor`, bei `leaf` nicht belegt. Sortierschlüssel: `todo` vor `backlog` → `rank` (ohne zuletzt) → Zahl der offenen transitiven `dependents` absteigend → `created` → `id`.
3. **Kein Kandidat:** Über die Issues im Kontext: W = `todo`/`backlog` mit `assignee` leer oder ich (also nicht bereit oder belegt) → `reason: 'waiting'`, `waiting` = W sortiert; sonst A = `in_progress`/`review` (außer meinen) oder `todo`/`backlog` mit fremdem Assignee → `'all_assigned'`; sonst `blocked`/`on_hold` vorhanden → `'all_blocked'`; sonst `'nothing_open'`.
4. **Hinweise** (immer): Gewähltes Issue mit `cancelled`/`rejected` in `depends_on` → `settled_dependency` mit diesen IDs; Issues im Kontext mit `isUnblockable` → `unblockable`, die Message sagt, welche Blocker `cancelled`/`rejected` statt `done` sind (§2.6).

Fensterverfahren (`value` setzt direkt, ohne Nachbarn anzufassen):

```
L = Issues mit rank außer id, nach compareIssues
k = top: 0 · bottom: |L| · before X: index(X) · after X: index(X) + 1
M = L mit id an Position k;  a = b = k
loop
  lo = a > 0 ? M[a−1].rank : −∞;  hi = b < |M|−1 ? M[b+1].rank : +∞;  n = b − a + 1
  lo = −∞ ∧ hi = +∞ → M[a+i] = STEP·(i+1)
  lo = −∞           → M[a+i] = hi − STEP·(n−i)
  hi = +∞           → M[a+i] = lo + STEP·(i+1)
  hi − lo − 1 ≥ n   → step = ⌊(hi − lo)/(n+1)⌋; M[a+i] = lo + step·(i+1)
  sonst             → a = max(a−1, 0); b = min(b+1, |M|−1); weiter
```

**Interfaces:**

Leer → `usage`; mehr als `MAX_BATCH` → `usage` mit Hinweis auf mehrere Batches. ### Task 13: Hand-Edits als Operationen

**Files:**
- Create: `src/ops/translate.ts`
- Modify: `src/store/layout.ts` (`classifyPath`)
- Test: `src/ops/translate.test.ts`, `src/store/layout.test.ts`

**Interfaces:**
- Consumes: `parseEntityFile`, `validateEntity`, `parseCommentFileName`, `bodyHash`, `applyBatch`
- Produces:
  - `type PathClass = { kind: 'issue'; id: string } | { kind: 'comment'; id: string; file: string } | { kind: 'attachment'; id: string; file: string } | { kind: 'user' | 'project' | 'sprint' | 'repo'; key: string } | { kind: 'config' } | { kind: 'other' }`; `classifyPath(path: string): PathClass` — `config` = `.backe/**`.
  - `type EditedFile = { path: string; before: string | null; after: string | null }` (Inhalt in `HEAD` bzw. Arbeitskopie; `null` = fehlt)
  - `type TranslateResult = { ops: Operation[]; manual: string[]; warnings: { path: string; unknownKeys: string[] }[] }`
  - `translateEdits(s: BacklogSnapshot, files: readonly EditedFile[], ctx: { actor: string }): TranslateResult` — `s` ist der Stand von `HEAD`. Ob gemischte Ergebnisse (Ops und `manual`) einen oder zwei Commits ergeben, entscheidet M5.

Regeln (§2.13 »Hand-Edits«): Eine Datei wird ganz übersetzt oder ganz `manual`. `manual` sind `attachment`, `config`, `other`, Dateien mit geänderten oder neuen unbekannten Keys, und Issue-Dateien mit geändertem `attachments`. Jede `after`-Datei wird geparst und validiert — Fehler wirft mit `datei:zeile`. Unbekannte Keys stehen in `warnings`.

- **Issue geändert:** `id`, `created`, `creator` geändert → `policy`; `paused_from` geändert ohne State-Wechsel → `transition` mit Hinweis auf `move`/`resume`. State geändert → `issue.move` mit `from`/`to` und bei `blocked` dem neuen `blocked_by`; der Endstand muss dem Ergebnis von `planTransition` entsprechen, sonst `transition`. Rank geändert → `issue.rank` mit `value`. Alles Übrige in **ein** `issue.edit`: `set` für `title`/`parent`/`assignee`, `add`/`remove` aus dem Mengenvergleich (Umsortieren allein ist keine Änderung) für `projects`, `sprints`, `repos`, `depends_on` und — nur ohne State-Wechsel — `blocked_by`; `props` je geändertem Key; `body` mit `from_hash = bodyHash(vorher)`, wenn sich der Body nach LF-Normalisierung unterscheidet.
- **Issue neu:** `issue.create` mit allen Feldern aus der Datei, Listen ausdrücklich (auch `[]`, sonst würde vom Parent geerbt); `creator ≠ actor` → `policy`. **Issue weg:** `issue.delete` mit `force: true`.
- **Kommentar** neu → `comment.add` mit `file`; Autor im Namen und im Frontmatter = `actor`, `created` passt zum Namen, `kind: transition` von Hand → `transition`. Geändert → `comment.edit`. Weg → `comment.delete`.
- **Projekt/Sprint/Repo/User:** neu → `project.create` · `sprint.create` (+ `entity.edit` für `closed`) · `repo.add` mit `name` · `user.add`; weg → `*.rm`; geändert → `entity.edit`.
- **Reihenfolge der Ops:** Users → Projekte (flach vor tief) → Sprints → Repos → neue Issues (topologisch nach `parent`, `depends_on`, `blocked_by` untereinander) → Issue-Änderungen → Kommentare → gelöschte Issues → gelöschte Repos, Sprints, Projekte (tief vor flach), Users.
